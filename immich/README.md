# Immich Integration

## Overview

**Immich** is a self-hosted photo and video server. This integration comes as
two protocols, the way `postgres://` and `postgres+bin://` do:

- `immich://` backs up one Immich user through the Immich API and restores the
  result into an Immich user, on the same server or another one. It needs
  nothing but an API key, so it works against hosted instances as well as your
  own.
- `immich+dump://` backs up a whole server the way Immich recommends: a fresh
  database dump taken through the admin API, plus the files of its
  `UPLOAD_LOCATION` when they are reachable. It restores with full fidelity,
  asset ids included, through the server's own maintenance restore.

The `immich://` protocol allows:

- Backing up a user's photos and videos as plain files, with their XMP sidecars
- Backing up the user's albums, stacks, tags, named people and face boxes
- Restoring into a fresh server or an existing user; what the target already has
  is skipped, albums and people of the same name are reused
- Restoring the originals alone to a directory with `plakar restore -to /path`

The `immich+dump://` protocol is documented [further down](#immichdump-a-server-as-a-dump-plus-files).

## Configuration

The configuration parameters are as follows:

- `location` (required): `immich://host[:port][/prefix]`. HTTPS is used unless
  the host is loopback; `plaintext=true` forces HTTP
- `api_key`: the Immich API key of the user. `PLAKAR_IMMICH_API_KEY` in the
  environment takes precedence and is the recommended way to pass it
- `insecure`: `true` to skip the verification of the server's TLS certificate
- `plaintext`: `true` to talk HTTP

The API key is created in Immich under *Account settings > API keys*. A key with
every permission is simplest; the backup needs `asset.read`, `asset.download`,
`assetFile.read`, `album.read`, `stack.read`, `tag.read`, `person.read` and
`face.read`, the restore needs the matching create and update permissions.

## Examples

```bash
# back up a user
$ export PLAKAR_IMMICH_API_KEY=...
$ plakar at /tmp/store backup immich://photos.example.org

# restore it into a fresh server, as another user
$ export PLAKAR_IMMICH_API_KEY=...
$ plakar at /tmp/store restore -to immich://127.0.0.1:2283 <snapid>

# restore the originals alone
$ plakar at /tmp/store restore -to /tmp/photos <snapid>
```

## Layout of a snapshot

```
/manifest.json                        server version, user, key permissions, counts
/assets/2024/07/IMG_0123.HEIC         original, bytes as-is
/assets/2024/07/IMG_0123.HEIC.xmp     XMP sidecar when Immich has one
/assets/2024/07/IMG_0123.HEIC.json    dates, favorite, visibility, EXIF, tags, people
/albums/<name>.json                   name, description, order, thumbnail, assets
/stacks/<primary sha1>.json           primary and members
/people/<name>.json                   name, birth date, face boxes
```

Assets are filed by the local date Immich shows them under. Two files with the
same name in the same month get the first eight hex digits of their SHA1
appended. Every relation is stored against the asset's SHA1 checksum, never
its path or Immich id, so the restore joins on content and the tree can be
reshaped without breaking restores.

## What a restore does

1. `POST /assets/bulk-upload-check` with every checksum: assets the target
   already has keep their id and are not uploaded again
2. uploads the rest, each with its sidecar, dates, favorite and visibility; the
   video of a live photo goes first so the image can point at it
3. creates the albums (or adds to an existing album of the same name), the
   stacks, the tags, the people (or reuses a person of the same name) and the
   face boxes
4. once the server has extracted the metadata of each uploaded asset, compares
   it with the snapshot and updates only what differs, sending the time zone
   along; a blind date update after upload would reset the zone

Errors in one item do not stop the others; they come back together at the end.

## What does not come back

- assets in the locked folder: API keys cannot see them, so they are not in the
  backup; a password session option is planned
- assets shared by a partner: the partner link belongs to the other user
- asset ids, creation dates, memories, shared links, the user's own API keys
  and PIN, OCR text (regenerated by the target)
- unnamed people found by machine learning, and the machine-learning origin of
  faces: restored faces come back as manual boxes on the same people, and the
  target's own face detection finds the rest

## Limitations of this version

- one user per location; a server backup is one task per API key
- no retries and no rate limiting
- the backup holds the metadata of every asset in memory before the first
  file is written, and lists sidecars and tags with one request per asset
- the restore stages the whole snapshot under the temporary directory before
  the first upload, so `$TMPDIR` needs as much free space as the library;
  the staging directory is removed when the restore ends
- uploads and the final metadata pass run one asset at a time; the metadata
  pass waits two minutes in all for the server's extraction queue and leaves
  the rest as uploaded

## immich+dump: a server as a dump plus files

`immich+dump://host[:port][/prefix]` takes an admin API key and talks to the
same server, but what it backs up is the server, not a user: every user,
password hash, API key, PIN, partner link, album, album share, person,
machine-learning face and asset id comes back. The price is that the files need
a shell on the host, as with the fs integration, and that a restore replaces the
target's database.

### Configuration

- `location` (required): `immich+dump://host[:port][/prefix]`
- `api_key`: an admin's API key, `PLAKAR_IMMICH_API_KEY` in the environment
  takes precedence. On a restore into a fresh server, a key that exists in the
  dump: it becomes valid once the dump is in
- `upload_location`: the server's `UPLOAD_LOCATION` as seen from this host.
  When set, the backup walks it after the dump and the restore writes it back
- `maintenance_token` (restore only): the maintenance token of a server that
  has no admin user yet, see below; `PLAKAR_IMMICH_MAINTENANCE_TOKEN` takes
  precedence
- `force` (restore only): `true` to restore a dump made by another Immich or
  Postgres version, or one whose name carries no version
- `dump_timeout` (backup only): how long to wait for the server's dump job,
  default `15m`
- `restore_timeout` (restore only): how long to wait for the maintenance
  restore, default `1h`
- `insecure`, `plaintext`: as for `immich://`

### Layout of a snapshot

```
/backups/immich-db-backup-20261112T092402-v3.4.0-pg14.19.sql.gz
/upload_location/upload/...        originals and sidecars
/upload_location/library/...       originals in external libraries
/upload_location/profile/...       avatars
/upload_location/backups/...       the dumps the server keeps itself
/upload_location/.immich           the marker files Immich checks at startup
```

The dump comes first, as Immich recommends: a backup taken while the server
runs can at worst hold files the database does not know about, never the
reverse. `thumbs/` and `encoded-video/` are left out, the server regenerates
them.

### What a backup does

1. `POST /api/jobs {name: backup-database}`, then polls
   `GET /api/admin/database-backups` until the new file is listed; the server
   writes a `.tmp` file and renames it at the end, so a listed dump is complete
2. streams the dump as `/backups/<filename>`
3. when `upload_location` is set, walks it with the fs integration's importer
   under `/upload_location/`

### What a restore does

1. reads the Immich and Postgres versions from the dump's filename and refuses
   the restore unless they match the target: Immich exactly, from
   `/api/server/about`; Postgres by major, from the dumps the target made
   itself, since nothing else exposes it. A target with no dump of its own
   skips the Postgres check and says so. `force=true` overrides both
2. uploads the dump with `POST /api/admin/database-backups/upload`, which
   stores it as `uploaded-<filename>`
3. `POST /api/admin/maintenance {action: restore_database}` with that name.
   The server dumps a restore point, restarts into its maintenance worker,
   restores, runs the migrations and restarts again. The exporter polls
   `GET /api/admin/maintenance/status` through the two restarts, where the API
   is away for a couple of seconds, and reports progress on stderr
4. writes `/upload_location/` back with the fs integration's exporter
5. `PUT /api/jobs/thumbnailGeneration {command: start, force: true}` when any
   file was written

One dump per restore: a snapshot with several gets the first applied and the
rest refused. Restore a single one with `plakar restore ... <snapid>:/backups`.

### Preconditions on the target

- a configured server (an admin exists): an admin API key is all it takes. The
  restore replaces the database; the server keeps a
  `restore-point-<ts>-v...-pg....sql.gz` in its backups folder to roll back
- a fresh server (no admin yet, Immich 3.x): the server has to be put in its
  restore flow first, with `POST /api/admin/database-backups/start-restore`
  (no auth) or *Restore from backup* on its setup page. It then restarts into
  maintenance mode and prints a login URL in its log, of the form
  `https://my.immich.app/maintenance?token=<JWT>`. That token, valid four
  hours, goes in `PLAKAR_IMMICH_MAINTENANCE_TOKEN`. Calling `start-restore` a
  second time mints a new secret and voids the first token. Without the
  token the restore refuses and says so; the restore never calls
  `start-restore` itself, since the token it would need is only in the log
- `upload_location` must be the directory the server mounts as
  `UPLOAD_LOCATION`; originals need not be in place before the dump is
  restored, the thumbnails are regenerated afterwards

### Example

```bash
# back up a server: dump plus files
$ export PLAKAR_IMMICH_API_KEY=...   # an admin key
$ plakar at /tmp/store backup -o upload_location=/srv/immich/library immich+dump://127.0.0.1:2283

# restore into a fresh server on another host
$ curl -X POST http://127.0.0.1:2283/api/admin/database-backups/start-restore
$ docker logs immich_server 2>&1 | grep -o 'maintenance?token=.*'
$ export PLAKAR_IMMICH_MAINTENANCE_TOKEN=...
$ plakar at /tmp/store restore -to immich+dump://127.0.0.1:2283 -o upload_location=/srv/immich/library <snapid>
```
